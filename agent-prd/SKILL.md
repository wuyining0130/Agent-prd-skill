# Agent PRD — AI Agent 需求文档生成器

## Purpose

引导式 AI Agent 需求文档生成器——通过结构化澄清对话，输出覆盖 Agent 设计、评测体系和约束条件的完整 Agent PRD。
适用于任何需要 LLM 驱动的自主决策系统：对话机器人、后台自动化 Agent、多 Agent 协作系统等。

与 `prd-draft` 的区别：`prd-draft` 面向传统 B 端 CRUD 功能；本 skill 面向智能体产品，
覆盖 Persona、Reasoning、Memory、Guardrails、评测体系等 Agent 特有维度。

## Instructions

### Codex 执行约定

- 不依赖特定交互工具名。优先在对话中用**一次一个问题 + 2-4 个建议选项**的方式推进；如果当前环境恰好提供交互式提问工具，可使用，但不是前提。
- 不为凑轮次而提问。目标是在**最少轮次**内拿齐关键信息；如果用户已经给了充分材料，可以少于 6 轮。
- 生成或修改文档时，使用当前环境可用的本地文件编辑方式；在 Codex 中优先精确修改，避免整篇覆盖已有文档。
- 涉及外部材料时，先读取真实文件内容再写结论；如果二进制文档难以直接读取，先转换或抽取文本，不要跳回旧版本模板。

### 加载知识

执行前先读取：
- `references/agent-prd-template.md` — 四章文档模板
- `references/clarification-guide.md` — 澄清问题库与分支逻辑
- `references/modification-mode.md` — 修改模式完整流程（M-Step 1-4）

---

### Phase 0: 判断模式

收到用户请求后，先判断是**新建**还是**修改**：

- **新建**：用户描述新的 Agent 需求 → 进入 Phase 1
- **修改**：用户说"改一下 Agent PRD"、"根据反馈更新"、"把 XX 补充进去"、"业务确认了 XX" → **先读取 `references/modification-mode.md` 获取完整流程**，然后按 M-Step 1-4 执行。不要跳过任何步骤。
  - **硬约束**：修改模式也必须重新执行 Phase 0.5 的材料扫描与冲突检测（如有新材料）；对受影响章节重新执行事实覆盖和来源回查
  - **一致性检查**：如果某章节修改会影响其他章节（如成功定义影响评测体系、能力拆解影响 3.7），必须联动修正，不能只改单段文本
  - **版本纪律**：任何修改必须升版本号 + 追加变更记录，无例外

---

### Phase 0.5: 材料扫描与冲突检测（新增）

**在进入澄清对话之前，如果用户提供了参考材料（文件、目录、文档链接），必须先执行本阶段。**

#### 1. 多版本材料扫描

同一主题可能存在多个文件版本（如 .md 模板 vs .docx 已填写版、会议纪要 vs 对齐文档）。扫描规则：

- **同名不同格式**：优先使用内容更完整的版本（如 `.docx`/`.extracted.txt` > 空白 `.md` 模板）
- **同主题多文档**：识别文档角色——模板（定义结构）vs 填写件（包含内容）vs 会议纪要（包含结论）。填写件和会议结论优先级高于模板
- **时间维度**：有明确日期的，新文档 > 旧文档
- **二进制文档处理**：如果用户提供的是 `.docx/.pdf/.pptx` 等二进制材料，先用可用工具读取/转换成文本后再参与优先级判断；不能因为文件难读就退回使用旧模板
- **输出**：在内部记录"材料优先级表"，后续生成时按此优先级取信息

#### 2. 关键事实提取

从所有材料中提取以下类型的关键事实，构建**事实清单**：
- 所有出现的**数字/阈值/百分比**（如"成本超 20% 调整"、"准确率 30-40%"）
- 所有**流程/时序描述**（如"前 2h 不动"、"每小时看一次"）
- 所有**权限/边界声明**（如"出价不放权"、"定向创建后不改"）
- 所有**判断 heuristics**（如"量级涨+成本涨→观察"、"好素材复制到 5-6 个账户"）

#### 3. 冲突检测与消歧

对比不同材料中的相同主题，检测口径冲突：

**输出格式——冲突事实表**（如有冲突）：
```
| # | 主题 | 材料A说法 | 材料B说法 | 推荐处理 |
|---|------|-----------|-----------|----------|
| 1 | 准确率目标 | 业务对齐文档：30-40%即可信 | 会议纪要：80-90% | 并列写清：门槛30-40% / 目标80-90%，适用对象不同 |
```

- 有冲突时：正文默认只保留最终采用的业务口径与适用对象；**冲突事实表**和消歧过程优先放入附录，不擅自取舍
- 无法判断时：正文相关处标注 `[冲突，待业务拍板]`，并在附录保留冲突说明

---

### Phase 1: 理解场景（静默，不输出）

收到用户需求描述后：

1. 提取关键信息：
   - 要自动化的业务是什么
   - 现在谁在做这件事
   - 核心痛点是什么

2. 判断 Agent 类型：
   - **对话交互型**：与用户实时对话，理解意图并执行
   - **后台决策型**：定时/事件驱动，独立完成分析和决策
   - **工作流编排型**：协调多个子任务/子 Agent，管理复杂流程

3. **能力模块拆解**（新增，必须执行）：
   从业务描述中识别 1-3 个核心能力模块。例如：
   - "素材识别" + "操作建议" 是两个不同能力
   - "意图理解" + "工单路由" + "答案生成" 是三个能力

   拆解后评估：
   - 各模块是否可以独立评测？
   - 各模块的输入输出是否解耦？
   - 是单 Agent 多能力，还是需要多模块/多 Agent？

   **结论影响 2.8 Orchestration 的写法**——不能无脑写"单 Agent 无需编排"

4. 预判需要重点澄清的板块

---

### Phase 2: 澄清对话（通常 4-8 轮，按需增减）

**规则**：
- 每轮**只问一个问题**
- 每个问题附带 **2-4 个选项**；默认直接在对话里给出，不依赖特定工具
- 如果当前环境有交互式提问工具，可以使用；没有也照常推进，仍保持"一次只问一个问题 + 附 2-4 个建议选项"
- 选项根据用户已给信息**动态生成**，不是照搬问题库
- 问题顺序按 clarification-guide.md 的编号，但措辞要自然口语化
- 用户选择后，简短确认并过渡到下一问
- 必问问题（Q1-Q7）全部覆盖，按需问题（Q8-Q10）根据触发条件决定

**对话风格**：
- 像一个有经验的产品架构师在和业务方对需求
- 不用术语轰炸，用类比帮助用户理解
- 用户回答简略时，主动补充合理默认值并确认

**结束条件**：
- 7 个必问问题全部有答案
- 按需问题根据上下文已覆盖或确认不需要
- 四大章节每个至少有基本输入
- 如果用户已提供高质量材料，允许合并减少轮次，但不能跳过关键缺口确认

---

### Phase 3: 生成 Agent PRD

基于澄清结果 + Phase 0.5 的材料分析，按 `agent-prd-template.md` 填充生成完整文档：

**生成原则**：

1. **第一章默认结构**：
   - 将“给谁用、典型场景、当前方式、痛点”融入 1.1“背景与目标”的业务背景部分
   - 只写直接使用 Agent 或基于其输出做决策的业务角色
   - 除非用户明确要求，否则不单列 1.2“用户角色与使用场景”
   - Phase 0.5 识别出的“材料冲突与消歧过程”默认不放正文，优先沉到附录；正文只写统一后的最终口径

2. **第二章默认写成完整的 Agent 设计，不再单列“知识资产与离线数据设计”大章**：
   - 第二章内部按 `2.1 Persona & Goal -> 2.2 Knowledge -> 2.3 Perception -> 2.4 Reasoning -> 2.5 Action -> 2.6 Memory -> 2.7 Guardrails -> 2.8 Orchestration -> 2.9 Evolution -> 2.10 一期交付物` 组织
   - `Knowledge` 回答“Agent 本来就知道什么”，只放慢变、可跨任务复用的知识；`Perception` 回答“Agent 这一轮实际看到什么”，只放快变运行时输入
   - 判断放 2.2 还是 2.3 的简单规则：如果信息在某次任务启动前就存在且可跨任务复用，放 2.2；如果它需要在每轮执行时查询、触发或计算得到，放 2.3
   - 原始业务文档、判断规则、字段语义、事件类型、案例经验通常写到 2.2；动态报表、事件 payload、当前配置值、预处理信号、记忆片段写到 2.3
   - 像 `roi_goal`、预算、阈值、出价范围这类动态参数配置，即使有业务含义，也优先写到 2.3.2“运行时配置清单”，不要伪装成“领域知识”
   - 同一张源表如果既是运行时读取源、又会沉淀成标注 / 回放 / 评测数据，必须拆开写：2.3 写“运行时读取”，3.1 写“离线资产”
   - 第二章中的 Knowledge 和 Perception 都要尽量明确**工程载体 / 存储位置 / 读取时机 / 运行时角色**；不要只写“注入方式”

3. **第二章默认写成“可直接开发的 Agent 设计”**：
   - Agent 靠 LLM 推理，**不是规则引擎**。绝对不要写 IF-ELSE 伪代码代替 Reasoning
   - 但如果用户明确说后续会自己实现、vibecoding、或希望文档达到生产可用水准，第二章必须写到工程可落地粒度：模块边界、输入输出、执行顺序、代码 / 规则 / LLM 职责边界、持久化产物、校验落点
   - 2.1 不是“给评审看的角色介绍”，而是顶层行为约束；至少要写清：角色边界、目标优先级、允许输出终态、默认失败策略，以及这些约束会落到哪里
   - 2.3 不只列“有哪些输入”，还要写清：谁在运行时读取、关键字段是什么、进入哪个下游模块
   - 2.4 除了判断维度、推理策略、思考链示例、不确定性处理，还要写清：哪些由代码做、哪些由规则做、哪些由 LLM 做
   - 2.5 到 2.8 至少回答四件事：动作怎么结构化输出、模块之间如何交接、硬约束在哪一层执行、端到端一轮任务如何跑完
   - 如果 2.1 里定义了“观察并复查 / 请求人工确认 / 无动作”等终态，2.5 的建议卡片 schema 和调度逻辑里也必须体现；不能只写在概念层
   - 如果用户明确表示 PRD 会直接作为开发依据，PRD 和技术文档的界限不必强行切开；优先保证研发一眼能看懂怎么实现
   - 好的写法："Agent 综合考虑用户情绪、问题紧急程度、历史处理结果来决定响应策略；预处理负责硬计算，规则层负责动作过滤，LLM 负责权衡与解释"
   - 坏的写法："IF 用户情绪==愤怒 THEN 安抚"

4. **2.8 Orchestration 的写法取决于 Phase 1 能力拆解结论**：
   - 如果确认是单模块/单能力：注明"本项目为单 Agent 架构，无需编排"
   - 如果有多个可独立评测的能力模块：描述模块间的协作方式（串行/并行/条件分发），即使实现上是单 Agent 也要说明内部能力的调度逻辑
   - **不能无脑写"单 Agent 无需编排"——必须基于能力拆解结论**

5. **2.9 Evolution**：
   - 如果项目不涉及持续学习，写清“通过人工复盘 + 提示词 / 规则 / 样本迭代”，不要展开冗长机制
   - 误判修正优先级默认放到第三章“持续监控与误判修正”，不要和 Agent 设计重复

6. **标注纪律——三级标注（强化版）**：
   - 只有源材料中明确写过的内容才能直接写入
   - 你基于推断补充的内容，按以下规则标注：
     - `[推断，待确认]`：涉及业务决策的推断（如金额阈值、SLA 要求、流程选择、权限边界），业务方必须明确拍板
     - `[推断，可沿用]`：行业通用实践的推断（如 API 重试 3 次、最小权限原则、日志审计），除非业务方有异议否则直接采用
     - `[待补充]`：完全没有信息的字段
   - **硬约束**：凡是 PRD 中出现的**数字、阈值、百分比、频率、时间窗口、权限边界**，如果不能在源材料中找到原文出处，**必须**标注 `[推断，待确认]` 或 `[待补充]`。无例外。
   - 错误的确定性比空白更有害——但过多的 `[待确认]` 也会让文档看起来不可用。用三级标注平衡"诚实"和"可读性"

7. **来源可追溯约束（新增）**：
   - PRD 中引用的**历史事实、项目沿革、数据结论**，必须能在源材料中找到对应原文
   - 如果某条信息只存在于模型的"常识推断"中、源材料里找不到依据，**不得写入正文**——要么放入附录标注 `[推断，待确认]`，要么直接不写
   - 特别注意：附录中的"项目历史""与前项目对比""数据验证结论"是最容易被模型脑补的部分，必须逐条对照源材料

8. 用用户的业务语言，避免空泛的模板话术
9. 表格中的示例行要替换为真实内容，不留占位符

10. **评测指标必须工程化（强化版）**：
   每个评测指标必须回答以下 6 个问题，缺一不可：
   - **谁标注**：人工标注（角色）/ 自动规则 / 模型自评？
   - **标注口径**：什么算"正确"？边界案例怎么判？多答案情况怎么处理？
   - **标注时机**：实时 / 每日 / 每周？标注滞后多久可接受？
   - **统计窗口**：按日/周/月统计？滑动窗口还是固定窗口？
   - **样本量要求**：多少条标注才有统计意义？置信区间要求？
   - **归因方式**（如适用）：回溯测试时，如何归因"是 Agent 建议带来的改善"vs"自然波动"？

11. **多模块指标不得混写（新增）**：
   - 如果 Phase 1 识别出多个核心能力模块，3.2 和 3.4 必须按模块分别定义指标、目标和放权条件
   - 某个模块已有明确数值目标（如"素材识别 80-90%"）时，**不得**自动推广为整个 Agent 或其他模块的目标
   - 其他模块没有数值目标时，写 `[待补充]` 或 `[冲突，待业务拍板]`，不要借用邻近模块的数字填空

12. **2.4 推理策略与思考链分工**：推理策略讲通用原则（每步 3-5 行），典型思考链讲具体场景的内心独白（引用格式）。两者互补不重叠——策略是"方法论"，思考链是"实战演练"

13. **2.5 Action 失败处理要区分可重试/不可重试**：幂等操作（查询类）可安全重试；非幂等操作（写入类）重试需谨慎。每个工具还应说明降级方案（如检索失败时用缓存兜底）

14. **双向事实覆盖与来源回查（新增，生成后必须执行）**：
    生成 PRD 后，必须做双向检查：
    - **正向覆盖**：对照 Phase 0.5 提取的事实清单，检查每条关键 heuristic 是否已映射到 Reasoning / Action / Guardrails / Evaluation 中的至少一处
    - **反向回查**：从 PRD 正文和附录中反向抽取所有**数字、阈值、百分比、频率、时间窗口、权限边界、历史结论**
      - 每一项都必须满足以下二选一：
        - 能回查到源材料中的对应原文
        - 已明确标注为 `[推断，待确认]` / `[推断，可沿用]` / `[待补充]`
      - 既没有来源、又没有标注的项 → 必须删除或补标
    - 未映射的事实 → 要么补充到 PRD 对应位置，要么在附录注明"该信息已知但未纳入一期范围"并说明原因
    - **输出两个比率**：
      - 事实覆盖率 = 已映射事实数 / 总事实数
      - 来源回查率 = 可回查或已标注的 PRD 事实数 / PRD 总事实数
    - 目标：两个比率都 ≥ 90%

**输出文件**：
- 文件名：`{需求名称}Agent需求文档.md`
- 位置：用户指定目录，若未指定则为当前工作目录或当前项目目录
- 使用当前环境可用的文件写入方式生成；在 Codex 中优先使用精确文件编辑能力，避免误覆盖用户已有内容

---

### Phase 4: 输出总结（必须执行）

生成 PRD 文件后，**必须**在对话中输出以下总结。这不是可选步骤——用户需要这个总结来快速了解文档状态和下一步行动。

```
## 完成情况

- 文件位置：{路径}
- 各章节完成度：
  - 一、背景与场景：{✅ 完整 / ⚠️ 部分待确认}
  - 二、Agent 设计：{✅ 完整 / 注明省略了哪些子章节及原因}
```
