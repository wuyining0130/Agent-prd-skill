# Agent PRD 修改模式

当用户要求修改已有 Agent PRD 时（如"改一下 Agent PRD"、"根据反馈更新"、"把 XX 补充进去"、"业务确认了 XX，更新一下"），进入修改模式而非重新走首次生成流程。

## Codex 适配说明

- 这里的"读取/修改/验证"是动作语义，不绑定某个厂商工具名。
- 在 Codex 中，优先先读取目标片段，再用精确补丁修改，最后回读验证；不要凭记忆整篇重写。
- 如果用户提供了新材料或新结论，即使改动很小，也要走完整的修改计划和版本管理流程。

## 触发条件

**任何对已有 Agent PRD 文件的修改都必须走完整的 M-Step 1-4 流程，没有例外。** 不存在"太小不值得走流程"的修改——哪怕只是更新一个 `[待补充]` 标注，也必须升版本号和追加变更记录。

满足以下任一条件时进入修改模式：
- 用户明确要求修改已有的 Agent PRD
- 用户提供了新的源材料（业务补充信息、会议结论、标注反馈等），要求更新 PRD
- 用户在对话中确认了某个 `[待补充]` 或 `[推断，待确认]` 项的结论
- 对话讨论中产生了需要写入 PRD 的决策（如"常规操作判断 80%+"）
- 用户要求根据技术方案反馈修正 PRD

## M-Step 1: 读取现有 PRD + 材料扫描

1. **读取当前 PRD**：读取 Agent PRD 文件，提取 frontmatter 中的版本信息（如 `版本：v0.2`）
2. **识别修改来源**：
   - **用户直接给出修改意见**：用户在对话中描述的变更要求
   - **新源材料**：用户提供了新的业务文档、会议纪要、标注数据等
   - **技术反馈**：技术方案评审发现 PRD 需修正的点
   - **混合来源**：以上多种组合
3. **对新材料执行 Phase 0.5**（如有新材料）：
   - 扫描新材料，提取关键事实
   - 与现有 PRD 中的事实做冲突检测
   - 输出新增/冲突事实清单

## M-Step 2: 生成修改条目清单（必须经用户确认）

**这是修改模式的核心步骤——不要跳过。** 列出所有计划修改的条目，逐条让用户确认后再动手。

输出格式：

```
📝 Agent PRD 修改计划（当前版本：{version}）

修改来源：{用户意见 / 新材料 / 技术反馈 / 混合}

---

### 计划修改项

| 编号 | 修改位置 | 修改类型 | 修改内容 | 来源 |
|------|----------|----------|----------|------|
| M-01 | 1.1 成功定义 | 修改 | 常规操作判断目标从 [待补充] 改为 80%+ | 用户确认 |
| M-02 | 3.4 达标标准 | 联动修改 | 同步更新常规操作判断达标线 | M-01 联动 |
| M-03 | 附录 B 待确认事项 | 关闭 | 移除已确认项 | 用户确认 |

### 联动检查预判

| 改了什么 | 需检查的联动章节 |
|----------|-----------------|
| 成功定义（1.1） | 2.1 Persona 成功指标、3.2 评估维度、3.4 达标标准 |
| 能力模块拆解 | 2.8 Orchestration、3.2 按模块拆分指标 |
| 操作禁忌 | 2.7 Guardrails、3.2 禁忌违反率指标 |
| 感知数据源变更 | 2.3 Perception 表、四、约束条件 |
| 知识库内容更新 | 2.2 Knowledge、2.4 思考链示例 |

### 不修改的项（说明理由）

| 跳过项 | 理由 |
|--------|------|
| {如有} | {理由} |

---

以上修改是否确认？可以：
1. 全部确认，开始修改
2. 逐条调整（告诉我哪条要改或不改）
3. 补充其他修改项
```

**修改类型说明**：
- **补充**：填充 `[待补充]` 或 `[推断，待确认]` 的确定值
- **修改**：改变现有内容（如修正数值、调整逻辑描述）
- **删除**：移除不需要的内容
- **新增**：新增此前没有的章节或维度
- **关闭**：待确认项已有结论，标注移除并写入正文
- **联动修改**：因其他条目的变更而必须同步更新

## M-Step 3: 执行修改

用户确认修改计划后，**逐条执行 读取→精确修改→验证 循环**，而不是凭记忆批量修改。

### 逐条修改流程（每个修改条目重复此循环）

```
对修改计划中的每一条 M-XX：

1. 读取 — 重新读取目标段落
   读取 PRD 文件中该条目涉及的章节（按章节或精确片段定位），
   确保看到的是当前最新内容（前面的修改可能已改变行号）

2. 精确修改 — 基于刚读到的原文执行修改
   补丁或编辑上下文必须从刚才读取的结果中复制，不要凭记忆拼写
   修改完成后记录该条目状态为 ✅

3. 验证 — 回读修改结果确认正确
   再次读取同一段落，检查：
   - 修改内容是否正确写入
   - 上下文是否被意外改动
   - 格式（表格对齐、列表缩进）是否正确
   如发现问题，立即修正后再进入下一条
```

**为什么必须逐条循环**：Agent PRD 通常 400-500 行，一次性读入全文后到执行修改时，早期内容已在 context 中衰减。凭记忆修改会导致 old_string 与实际文本不匹配，造成静默跳过或改错位置。

### 修改执行规则

1. **局部修改，非整篇重写**：只修改确认的条目涉及的章节，其他内容保持原样不动。优先使用精确补丁或等价的局部编辑方式，禁止整篇覆盖

2. **版本号递增**：更新文档头部的版本号
   - `v0.1` → `v0.2` → `v0.3`（修改迭代）
   - 同步更新日期

3. **在附录中追加变更记录**（如附录无此表则新建）：

```markdown
### X. 变更记录

| 版本 | 日期 | 变更内容 | 来源 |
|------|------|----------|------|
| v0.3 | 2026-05-22 | M-01: 常规操作判断目标确认为80%+; M-02: 联动更新达标标准表 | 用户确认 |
| v0.2 | 2026-05-21 | 初始完整版本 | agent-prd skill 生成 |
```

4. **标注状态联动更新**：
   - 用户确认了某个 `[待补充]` → 移除标注，写入确定值
   - 用户确认了某个 `[推断，待确认]` → 移除标注（确认采用）或修改为确认值
   - 修改引入了新的不确定点 → 新增 `[待补充]` 或 `[推断，待确认]`
   - 附录 B "待确认事项" 同步更新（关闭已确认项、新增未确认项）

5. **Agent PRD 特有的联动映射**：

   | 改了什么 | 必须检查的联动章节 |
   |----------|-------------------|
   | 成功定义（1.1） | 2.1 成功指标、3.2 评估维度、3.4 达标标准 |
   | 能力模块定义 | 2.8 Orchestration 模块划分、3.2 按模块分指标、3.4 按模块分目标 |
   | 感知数据源（2.3） | 四、约束条件中的数据刷新 / 接口要求 |
   | 操作禁忌（2.7） | 3.2 禁忌违反率指标定义 |
   | Knowledge（2.2） | 2.4 推理中引用的知识、2.4 思考链示例 |
   | Action 工具 / 权限（2.5） | 2.7 高危操作表、放权阶段表 |
   | 评测指标定义（3.2） | 3.4 达标标准表 |
   | 附录 D 事实覆盖表 | 如果正文改了映射关系需同步 |

6. **受影响章节重新执行事实覆盖与来源回查**：
   - 对被修改的章节，重新检查：每个数字/阈值是否有源材料出处或已标注
   - 如果新材料引入了新事实，检查是否已映射到 PRD 对应位置
   - 更新附录 D 的事实覆盖表（如有变动）

7. **全量验证（所有条目完成后）**：快速通读整个 PRD，检查：
   - 所有修改条目是否都已正确落地
   - 章节编号是否因增删内容而错乱
   - `[待补充]` / `[推断，待确认]` 标注是否与附录 B 一致
   - 新增事实是否在附录 D 事实覆盖表中有记录

## M-Step 4: 修改总结

修改完成后输出：

```
✅ Agent PRD 已更新：{版本号}

**本次修改：**
- M-01: ✅ 已完成 — {简要说明}
- M-02: ✅ 已完成 — {简要说明}（联动）
- M-03: ✅ 已完成 — {简要说明}

**事实覆盖影响：**
- 新增覆盖事实：{N} 条
- 事实覆盖率变化：{旧} → {新}

**标注状态变化：**
- [待补充] 关闭：{N} 个
- [推断，待确认] 关闭：{N} 个
- 新增待确认项：{N} 个
- 剩余 [待补充]：{N} 个
- 剩余 [推断，待确认]：{N} 个

**建议下一步：**
- {根据场景选择：如果关闭了多个待确认项，建议检查是否可以推进到下一阶段；
  如果新增了事实，建议重新验证技术方案是否需要同步更新等}
```

## 修改模式的原则

**先列清单再动手**：这是与首次生成模式最大的区别。首次生成时 AI 有较大自由度，修改时必须精确——用户已经在前一版上投入了评审精力，不能随意改动未经确认的内容。

**最小化改动**：只改用户确认的条目。不要"顺手"修改其他章节的措辞、重新排版段落、或调整未提及的内容。如果发现其他问题，列入总结的"建议"中提醒用户，而不是擅自修改。

**对话中的用户补充必须落地**：修改过程中用户可能随口补充新信息或纠正之前的说法。处理规则：
- **新增信息**：追加为新的修改条目（M-XX），标注来源为"对话补充"
- **与已有内容冲突**：以用户最新表述为准——用户在修改轮次中的纠正代表最新意图
- **落地方式**：在当前修改批次中一并执行，不要说"下次再改"

**任何修改必须升版本**：无论修改多小，只要对 PRD 文件做了编辑，就必须同步完成：（1）版本号递增；（2）变更记录追加。没有例外。版本号是 PRD 读者判断"看的是不是最新版"的唯一依据。

**保持可追溯**：每次修改都有变更记录，每个修改条目都有来源标注。这样用户回顾 PRD 演变历程时能清楚每个变化的原因。

**来源回查纪律不降级**：修改模式下同样遵守"数字/阈值必须有来源或标注"的硬约束。用户口头确认的数值，来源标注为"用户确认 + 日期"即可，但不能无来源无标注。
