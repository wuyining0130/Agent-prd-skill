# Agent PRD Skill

通过结构化澄清，把一个 AI Agent 想法、业务材料或已有需求，整理成可评审、可追溯、可供研发继续落地的 **AI Agent 需求文档**。

适合产品经理、业务负责人，以及需要把 Agent 方案讲清楚的开发者。支持对话交互型、后台决策型和工作流编排型 Agent，也适用于 Copilot 与多能力协作场景。

本仓库同步自维护者当前使用的 `agent-prd` skill，同步日期为 **2026-09-30**。它是一套给 AI 助手使用的 Markdown 工作指令、问题库和模板。

## 核心能力

| 能力 | 具体做什么 | 对使用者的价值 |
|---|---|---|
| 结构化需求澄清 | 覆盖项目与场景、人工流程与痛点、知识来源、角色与成功标准、工作流程、工具依赖、安全边界；按需补充评测、记忆和成本等约束 | 先补齐关键决策，再生成文档，减少反复重写 |
| 多材料梳理与冲突检查 | 区分模板、已填写文档、会议结论和不同版本；提取数字、时间窗口、权限和业务判断经验；标出冲突 | 避免遗漏业务规则，或把不同材料中的口径混在一起 |
| Agent 能力拆解 | 识别核心能力模块，判断输入输出是否解耦、能否独立评测，并描述串行、并行或条件分发关系 | 说明单 Agent 内部能力如何协作，或为什么需要多模块编排 |
| 完整 Agent 设计 | 覆盖角色与目标、感知、推理、动作、记忆、安全边界、编排、持续改进和一期交付物 | 不只描述功能，还讲清一次任务如何完成 |
| 知识与规则按职责归属 | 将数据语义、判断原则、动作约定、案例和硬约束写入实际承载模块，保留来源、维护、读取及版本要求；独立知识库或检索能力按需设计 | 避免重复维护口径，明确每条经验如何进入系统并生效 |
| 面向研发的细化 | 需要直接开发时，补齐模块边界、输入输出、执行顺序、代码／规则／LLM 分工、结构化动作及校验位置 | 为技术方案或后续开发提供更明确的依据 |
| 评测体系设计 | 定义指标、标注角色与口径、标注时机、统计窗口、样本量、归因方式、测试方案和达标标准；不同模块分别设目标 | 让“效果好”变成可验证的验收规则 |
| 事实追溯与不确定性标注 | 检查源材料事实是否进入 PRD，反查文档中的数字和结论是否有依据；区分推断和缺失信息 | 降低将模型补充内容误当成业务结论的风险 |
| 已有 PRD 的受控修改 | 读取当前版本，提出修改计划，经确认后逐条局部修改；同步关联章节、待确认项、版本号和变更记录 | 保留已有评审成果，让需求演变可追踪 |

## 会产出什么

主要产物是 `{需求名称}Agent需求文档.md`，包含四章及附录：

1. **背景与场景**：业务背景、使用角色、典型场景、痛点、目标、成功定义、一期范围与非范围。
2. **Agent 设计**：Persona & Goal、Perception、Reasoning、Action、Memory、Guardrails、Orchestration、Evolution，以及一期交付物。
3. **评测体系**：评测与对齐数据资产、评估指标及统计口径、测试方案、达标标准、持续监控与误判修正。
4. **约束条件**：延迟、成本、并发、可用性、合规及开发前置依赖。
5. **附录**：术语、待确认事项、变更记录、事实覆盖与来源回查、材料冲突及采用口径。

默认不单列 Knowledge 章节。知识与专家经验按实际职责分配到各模块；有明确的独立知识库、文档检索或知识维护需求时，可增设对应章节。修改已有 PRD 时沿用实际结构，不自动补回已取消的章节，也不未经授权迁移原有内容。

交付时还会在对话中汇总章节完成度、冲突处理、待确认／待补充事项及下一步建议。

默认输出到用户指定目录；未指定时使用当前工作目录或项目目录。已有旧名称文档会沿用实际路径，不因为命名规则变化另建重复副本。具体项目的路径与协作约定应在使用时提供。

## 工作方式

### 新建文档

```text
识别新建需求
  → 扫描参考材料、提取事实、识别冲突（有材料时）
  → 理解业务场景并拆解能力模块
  → 逐步澄清关键缺口
  → 生成四章 Agent PRD
  → 检查事实覆盖与来源
  → 汇总完成度和待确认项
```

澄清通常为 4–8 轮，一次一个问题，配合 2–4 个建议选项。已有充分材料时可减少轮次；复杂场景可增加，重点是覆盖关键问题。

### 修改文档

```text
读取现有 PRD 与新材料
  → 列出修改条目及跨章节影响
  → 用户确认修改计划
  → 逐条读取、局部修改、回读验证
  → 更新关联章节、版本号与变更记录
  → 复查受影响事实并输出修改总结
```

当前 skill 对 PRD 修改采用严格版本纪律：包括补充待确认项在内的修改，也要求更新版本和变更记录。使用项目中若有更高优先级的明确约定，需同时遵循。

## 安装与使用

### 在 Codex 中安装

可以直接让 Codex 使用 skill-installer 安装仓库中的目录：

```text
请使用 skill-installer，从 https://github.com/wuyining0130/Agent-prd-skill 安装 agent-prd 目录。
```

也可以先克隆仓库，再把完整的 `agent-prd/` 文件夹复制到项目的 `.agents/skills/` 或个人的 `~/.agents/skills/` 下。目标结构应为 `.../skills/agent-prd/SKILL.md`，并保留全部 `references/` 文件。已有同名 skill 时，应先确认要使用的版本。

Codex CLI／IDE 可通过 `$agent-prd` 显式调用，也可根据需求内容匹配。安装位置和发现机制参考 [OpenAI 官方 Skills 文档](https://developers.openai.com/codex/skills/)。

### 示例一：从想法开始

```text
$agent-prd
帮我设计一个客服工单分流 Agent，面向客服主管。
现在人工阅读工单、判断紧急程度，再分配给不同团队。
一期只提供分流建议，由主管确认后执行。
请先澄清关键问题，再输出到 requirements/工单分流/。
```

### 示例二：基于材料生成

```text
$agent-prd
请读取我提供的业务说明、会议纪要和现有规则，整理广告优化建议 Agent 的 PRD。
先识别口径冲突，缺少依据的数字和权限边界不要直接写成已确认结论。
这份文档会作为后续开发依据，请细化模块输入输出、执行顺序和验收口径。
```

### 示例三：更新已有文档

```text
$agent-prd
请根据新的业务确认，更新 requirements/工单分流/工单分流Agent需求文档.md。
新增要求：高风险工单必须转人工，普通工单仍只输出建议。
请先列出修改计划和受影响章节，确认后再更新版本及变更记录。
```

使用时最好提供：业务目标、当前人工流程、已有材料、允许的自动化程度、成功标准、硬性约束、输出目录，以及文档是否会直接作为开发依据。

## 质量机制与能力边界

### 不确定信息如何处理

| 标注 | 含义 |
|---|---|
| `[推断，待确认]` | 涉及业务决策的推断，需要业务方确认 |
| `[推断，可沿用]` | 通用实践的建议，可在无异议时采用 |
| `[待补充]` | 当前缺少信息 |
| `[冲突，待业务拍板]` | 材料之间存在尚未解决的口径冲突 |

其中，数字、阈值、频率、时间窗口和权限边界采用更严格的来源要求：没有原文依据时，必须标为待确认或待补充，不应仅凭通用经验视为已确定。

### 两项文档检查指标

- **事实覆盖率**：已映射到文档的关键事实数 ÷ 源材料关键事实总数。
- **来源回查率**：有原文依据或明确标注的 PRD 事实数 ÷ PRD 事实总数。

skill 将两者的目标设为 **≥ 90%**。这是生成文档时的检查目标，不是已测得的效果、业务准确率承诺或“所有内容都已确认”的证明；来源回查率也包含已明确标注的不确定信息。没有源材料或分母为零时，不能据此宣称 100% 覆盖。

### 运行依赖与当前边界

- 需要能读取这些 Markdown 指令并进行对话的 AI 助手；保存产物需要文件写入能力。
- 仓库本身没有脚本、模型服务、API 集成或专用文档转换器。读取 Word、PDF、PPT 或在线材料，依赖宿主环境提供相应工具与访问权限。
- 能规划评测体系、工具调用和运行流程，但不会凭这套文档自动完成业务 API 接入、训练模型、执行评测或部署 Agent。
- 不能替业务方批准权限、阈值或自动化边界；推断与待确认事项仍需要相关人员决策。
- 模板含建议卡片、运行时配置等设计示例，生成时应按实际业务替换；支持的类型不等于已对所有业务场景完成效果验证。
- 可衔接 `tech-design` 等后续工作，但这些 skill 不包含在本仓库中，也不是本 skill 的安装依赖。
